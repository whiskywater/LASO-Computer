# Security model

## Authorization and capabilities

Each invocation goes through the endpoint policy before a provider is called. The default decision is `deny`; LASO authorization cannot enable an action that endpoint policy denies. Capabilities are named individually, including `screen.capture`, `pointer.move`, `pointer.click`, `keyboard.type`, `keyboard.key`, `clipboard.read`, `clipboard.write`, `window.list`, `window.focus`, `ui.inspect`, `ui.invoke`, `browser.status`, the Playwright `browser.*` actions, and `shell.execute`. `browser.status` reports only the visible top-level window count and whether a supported browser window is visible or foreground; it does not return window titles or process paths.

The implemented policy decisions are `allow`, `deny`, and `require_approval`. Core's current worker-process v1 contract documents correlated `approval`, `permission`, and `question` requests with worker responses. LASO-Computer does not yet implement that process-worker interaction channel, so endpoint `require_approval` remains fail-closed until adapter integration and end-to-end tests pass. LASO-Computer does not emit unsolicited interaction frames between protocol requests.

## Plugins and adapters

Provider registration never grants permission. An untrusted provider's capabilities remain subject to the same endpoint policy and argument/result bounds. The registry exposes per-provider identity, version, declared capability schemas, health, invocation, cancellation, and lifecycle. Native providers currently run in-process; an in-process C++ provider is trusted code and therefore must come from this reviewed build. Arbitrary dynamic DLL loading is not supported.

The Playwright MCP adapter is a separate AppContainer process with a fixed operation set, bounded protocol I/O, timeout/cancellation, explicit stdio handles, and a kill-on-close Job Object capped at one process. C++ launches and owns Edge separately with its normal Chromium sandbox, a managed per-run profile, a loopback-only CDP port, and a separate kill-on-close Job Object. The user Edge profile is never selected. MCP receives read/execute access only to the configured Node directory and pinned package tree, plus read/write/execute/delete on its unique provider temp directory; it cannot access the Edge profile. Added provider ACL entries are revoked on shutdown. The Node AppContainer has no network capabilities and the Job Object prevents it from spawning a child process.

A rejected experiment used `CreateRestrictedToken(DISABLE_MAX_PRIVILEGE)` without a restricting SID. At Medium Integrity it passed the browser fixture, but `IsTokenRestricted` was false and the provider could read and write a generated outside-runtime file; only the Job Object blocked child-process creation. Low Integrity prevented browser attachment. `WinRestrictedCodeSid` as a restricting SID caused Node to exit `0xC0000142` with the runtime-only ACLs tested. This weaker token mode was removed from production configuration; it must not replace AppContainer. Details and a repeatable manual probe are in [the restricted-token experiment](restricted-token-experiment.md).

Node's `fs.realpath` fails in this AppContainer because the Windows `GetFinalPathNameByHandleW(..., VOLUME_NAME_DOS)` conversion is denied even though `CreateFileW` can open the provider output. Exact non-inheriting `FILE_TRAVERSE`, `FILE_READ_ATTRIBUTES`, and combined ACE attempts did not help and were restored. No broad volume permission was granted. The pinned MCP's documented `--allow-unrestricted-file-access` option skips its own workspace/file-URL guard; this means the AppContainer ACL and C++ adapter are the security boundary. A generated outside-file read and write both failed with `EPERM`, and Node could not spawn `whoami.exe` under the one-process Job Object. C++ rejects direct `file://` URLs; an HTTP fixture link to a generated test file did not navigate Edge off the HTTP page or expose the test marker. No MCP filesystem tool, arbitrary MCP passthrough, arbitrary JavaScript, cookies/storage, uploads, or downloads are exposed. Keep the fixed typed tool map and narrow AppContainer ACLs.

Current Windows testing shows AppContainer MCP needs loopback permission to reach C++-owned Edge's local CDP endpoint. With the exemption list empty, MCP's GET to `127.0.0.1:<dynamic-port>` times out; the same endpoint and MCP package passed the fixture outside AppContainer. This is consistent with Windows AppContainer loopback isolation. No exemption was added during the unattended investigation. The broker can query and remove only the fixed legacy exemption; it cannot add one. Any future narrowly scoped enablement requires an explicit attended security decision. CDP itself has no authentication; a same-user local process that discovers the ephemeral loopback port could attach. Same-user compromise and administrators are outside this containment claim. Node's main-entry volume-root probe is avoided with `--preserve-symlinks-main`.

## Privileged development broker

The optional `LASOComputerBroker` service is installed/updated/uninstalled only through an attended administrator bootstrap. It runs as LocalSystem because Windows loopback-exemption configuration is machine-wide, but it exposes only a local, versioned named-pipe protocol for status, fixed AppContainer SID lookup, querying the exact legacy exemption, and removing only that exemption. The pipe rejects remote clients, its DACL names SYSTEM and the bootstrapped user SID, and the service impersonates and verifies the interactive caller. There is no shell, arbitrary process launch, ACL editor, registry editor, firewall editor, or exemption-add operation. Requests and replies are bounded and strict; privileged operations are audited. See [unattended Windows development](unattended-windows-development.md) for bootstrap and threat model.

## Process execution

`shell.execute` is a legacy capability name; it executes a program directly and never invokes a shell. It requires an exact absolute executable path allowlist. Arguments have count/size limits, command-line quoting follows Windows process rules, the child receives only explicitly allowed environment variables, the working directory is a controlled temporary directory, output is bounded and marked if truncated, and timeout/cancellation terminates the child job. UNC and reparse-point path surprises are rejected where checked. Broad executable allowlists are unsafe.

## Validation and data bounds

The worker transport enforces a 1 MiB maximum JSON frame centrally on reads and writes. Malformed JSON, duplicate/conflicting request identifiers, invalid payloads, and oversized frames fail as protocol errors. Structured data and capability results are separately bounded. Clipboard and structured UI reads fail if their limit is exceeded; process output carries explicit truncation metadata.

## Audit and privacy

Audit events attribute caller/session/job, provider, capability, policy decision, outcome, and timing. They do not include user arguments, typed text, clipboard values, URLs, screenshots, or process stdout/stderr. Audit storage is local. A host administrator can still inspect process memory and endpoint files; this design does not claim protection from a compromised Windows account or administrator.

## Transport and limitations

There is no inbound listener and no remote endpoint enrollment. The supported operating model is a locally supervised process with stdin/stdout. The worker parses bounded process-worker v1 frames and supports `hello`, `submit`, `status`, `result`, `cancel`, and `shutdown`; each submitted capability is checked by local endpoint policy. Correlated approval, permission, and question interactions are not implemented, so `require_approval` remains denied. End-to-end Core acceptance and Windows CI for this adapter are still pending.
